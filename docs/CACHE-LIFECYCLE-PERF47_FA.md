# کش، چرخهٔ عمر و «حذف/به‌روزرسانی سرِ وقت» — P-PERF-47

**تاریخ:** 2026-09-16 · **منبع مشترک:** `Biotak-Trigger-TH3-mql4/Biotak` · **وضعیت:** پیاده‌سازی و تست‌شده

---

## ۱. ریشهٔ واقعی — با عدد، نه با حدس

سؤال شما این بود: «چرا در MT4 روان و سریع روشن/خاموش می‌شود و اینجا نه؟»

پاسخ در یک جدول است. پروبِ نصب‌شده روی ترمینال زندهٔ MT5 (`MT5PrimitiveProbe`) هر primitive را زمان‌بندی کرد:

| primitive | هزینهٔ هر فراخوانی |
|---|---|
| `GlobalVariableSet` | 0.128 µs |
| `ChartSetInteger` | 0.128 µs |
| `ObjectSetInteger(XDISTANCE)` | **0.245 µs** |
| `ObjectSetString(TEXT)` | 0.369 µs |
| `ObjectCreate + Delete` | 0.588 µs |
| `iBars` / `iClose` | 0.03 / 0.06 µs |
| `ChartRedraw` | 2.14 µs |
| `ObjectName(0,0)` | 31.7 µs |
| `ChartGetInteger(WIDTH)` | 33.5 µs |
| `ObjectGetInteger(TYPE)` | 33.7 µs |
| `ObjectsTotal(0,-1,-1)` | 33.8 µs |
| `ObjectFind(existing)` | 51.7 µs |
| **`ObjectFind(missing)`** | **88.0 µs** |

**نتیجهٔ کلیدی: MT5 برای «نوشتن» پول نمی‌گیرد، برای «پرسیدن» پول می‌گیرد.**
فاصلهٔ ارزان‌ترین نوشتن تا گران‌ترین خواندن **۳۶۰ برابر** است. و گران‌ترین primitive روی کل چارت
دقیقاً همان چیزی است که هر «آیا این شیء وجود دارد؟» هزینه می‌کند: `ObjectFind(missing)` با ۸۸ میکروثانیه.

تمام باگ‌های این دور از یک جنس‌اند: **کدی که از ترمینال چیزی می‌پرسد که خودش جوابش را می‌دانست.**

## ۲. سناریوهای مخرب — تیتروار

### ۱) هر سوییچ تایم‌فریم ۷۳۴ میلی‌ثانیه توقف در teardown
```
[W][PERF] OnDeinit reason=3 took 734ms (budget 150ms)
[W][PERF] OnDeinit breakdown: pnl=437ms menu=0ms htf=219ms save=0ms cleanup=0ms handler=78ms
```
سوییچ تایم‌فریم = یک جفت `deinit + init`. یعنی این ۷۳۴ms **قبل از اینکه نمونهٔ جدید شروع کند** پرداخت
می‌شود؛ کاربر همان «فسفس» را می‌بیند.

**مقایسهٔ ساید-به-ساید با MT4 (همان روز، همان منبع مشترک):**

| | MT4 (AMarkets، زنده) | MT5 (Vittaverse، زنده) |
|---|---|---|
| هشدار بودجهٔ OnDeinit | **صفر در کل روز** | **۱۱ مورد در ۲۰ دقیقه** |
| کل سوییچ Full | **۴۲ ms** (uninit 00:19:55.367 → init 00:19:55.409) | ۷۳۴ ms فقط در teardown |

یعنی یک رگرسیون واقعی و قابل‌اندازه‌گیری، نه توهم.

### ۲) `PnlCloseAll` برای پاک‌کردن یک خانوادهٔ **خالی** حدود ۵۶۰ سؤال پرسید
`PnlCloseAll` روی **هر ۱۴ پنل** `PnlDestroy(i)` صدا می‌زد، در حالی که **حداکثر یکی** روی صفحه است —
چون `PnlOpen` قبل از ساختن، `PnlCloseAll` را صدا می‌زند (`BiotakPanels.mqh:6441`). پس ۱۳ تا از ۱۴
teardown روی خانوادهٔ خالی کار می‌کرد، و هر کدام باز هم یک اسکن کامل چارت + پروب‌های خودش را
پرداخت می‌کرد. این همان `pnl=437ms` است.

### ۳) اسکن دوم و ۳۳ پروبِ `PnlDestroy` تضمیناً «miss» بودند
`PnlDestroy` بعد از `ObjectsDeleteAll(0, head, ...)` یک **اسکن کامل دوم** (`head+"card"`) و حدود
**۳۳ تا `ObjectDelete(0, head+...)`** دیگر می‌زد. همهٔ آن اسم‌ها زیرمجموعهٔ اکید پیشوندی بودند که
خط قبل پاک کرده بود (`PnlName`/`PnlHead` در `:2472`/`:2476` هر شیء این خانواده را
`btnPrefix + "Pnl" + item + "_" + ...` می‌سازند و `head` دقیقاً همان است). پس ۳۳ miss تضمینی × ۸۸µs.

### ۴) `CacheClear()` وقتی کش خالی بود **نمی‌توانست** امضای رندر را باطل کند
`MarkDrawGeneration()` در **انتهای** تابع و **پشت دو early-return** بود (`!initialized` و `size==0`).
معنای این bump «چارت دیگر آنچه رندر کردیم را ندارد» است — این حقیقتی دربارهٔ **چارت** است، نه دربارهٔ
جدول. پس هر فراخوانی‌کننده‌ای که خانواده را پاک می‌کرد و بعد `CacheClear()` می‌زد تا امضای هندسی را
باطل کند، **هیچ** نمی‌گرفت اگر کش اتفاقاً خالی بود (نمونهٔ تازه، یا خانواده‌ای که هرگز کش نشده —
`ClearFactorLevels` دقیقاً همین شکل است). نتیجه: قاب بعدی با امضای هندسی کهنه مقایسه می‌شد،
`geometryChanged` نادرست می‌شد و **رندر انجام نمی‌شد** — تصویر تا وقتی چیز نامرتبطی حرکت کند غلط می‌ماند.
این همان نیمهٔ «سرِ وقت باطل نمی‌شود» شکایت شماست.

### ۵) فیلتر `'T','H'` در `CacheRebuild()` — تلهٔ نهفته
فیلتر «این مال ماست؟» دو حرف سخت‌کدشده بود. **هم در آن واحد خیلی تنگ و هم خیلی گشاد:**
- **تنگ:** `inpObjectPrefix` یک input است؛ کاربری که اسمش را عوض کند بی‌آنکه با `TH` شروع شود،
  هر rebuild **هیچ** کش نمی‌کند. خانوادهٔ `BiotakHTF_<chartId>_<i>` را هم به‌کل از دست می‌دهد.
- **گشاد:** شیء بیگانه‌ای که اسمش تصادفاً با `TH` شروع شود، به‌عنوان **مالِ ما** کش می‌شود.

امروز کد مرده است (فقط test harness صدایش می‌زند) — و همین باعث شد کسی باگ را نبیند.

### ۶) دامنهٔ جدول «عدمِ وجود» در برابر سوییچ تایم‌فریم
علامت‌های P-PERF-07 با `g_drawGeneration` محدود می‌شوند و سوییچ TF آن را بالا می‌برد، پس اولین
teardown بعد از سوییچ قیمت کامل می‌دهد. **این رفتار درست است** (سوییچ، حقایقِ چارت را باطل می‌کند)
و حالا به‌خاطر اصلاح‌های ۲ و ۳ ارزان است.

### ۷) `labels=954ms` — آیتم باز
```
[W][PERF] chart change breakdown: redraw=0ms labels=954ms tail=0ms   (SPXUSD H1→M30)
```
`RedrawLabelsOnly()` بودجهٔ حدود یک ثانیه را روی یک resize می‌سوزاند. این هنوز درمان نشده.

## ۳. باگ‌های UI پنهان که پیدا شد

1. **اختلاف دامنهٔ پنجره.** `ObjectDelete(0, name)` **همهٔ** subwindow‌ها را می‌گشت، ولی
   `ObjectsDeleteAll(...,0,...)` فقط پنجرهٔ ۰ را. یعنی یک شیء سرگردان در subwindow از teardown قدیمی
   **جان سالم به در می‌برد**. (اصلاح شد: پنجرهٔ `-1`.)
2. **`BkDdClose()` فقط برای item 13 صدا زده می‌شد.** اشیاءش زیر `Pnl13_` هستند و پوشش داشتند، ولی
   **state** آن (`g_BkDd`) اگر پنل دیگری teardown می‌شد ریست نمی‌شد. حالا یک‌بار در هر close.
3. **`PnlDdClose()` چهارده بار در هر close** صدا زده می‌شد. idempotent است، ولی ۱۳ فراخوانی بی‌اثر
   هرکدام یک مقایسه هزینه داشتند. حالا یک‌بار.
4. **کلاسِ باگِ P-UI-71 (سقفِ فهرست دستی).** فهرست دستی سقف داشت و هر کارتی که از سقف بزرگ‌تر می‌شد
   ردیف‌هایش را برای همیشه روی چارت جا می‌گذاشت. حالا **تنها مکانیزم، پاک‌سازی پیشوندی است** — پس این
   کلاس دیگر بسته است، چون پاک‌سازی پیشوندی نمی‌تواند از drawer جدا بیفتد.

## ۴. راه‌حل یکپارچه — یک قاعده، همه‌جا

> **سؤالی که برنامه جوابش را می‌داند هرگز از ترمینال پرسیده نمی‌شود؛
> و یک خانواده با «یک پیشوندِ نام» حذف می‌شود، نه با فهرستی از حدس‌ها.**

سه نتیجهٔ مستقیم:

| قاعده | چرا |
|---|---|
| **پاک‌سازی پیشوندی برای teardown** | کامل *به‌حکم ساختار* است و **نمی‌تواند نشتی بدهد**؛ یک اسکن جای ۲۸ اسکن. یک ledger («کدام پنل ساخته شده؟») فقط به‌اندازهٔ همهٔ نویسنده‌هایش درست است و پنلی که روی چارت است ولی flag‌اش false، **بی‌صدا** جا می‌ماند — یعنی همان کلاسِ شبحی که P-UI-71 با آن جنگید. |
| **bump نسل، بی‌قید و شرط** | ابطال، حقیقتی دربارهٔ چارت است نه دربارهٔ جدول. |
| **«مالِ ما» = پیشوندِ شیء** | هرگز یک جفت حرفِ سخت‌کدشده. |

## ۵. آنچه پیاده و تست شد

| فایل | تغییر | جایگزینِ |
|---|---|---|
| `Biotak/ObjectCache.mqh` | `MarkDrawGeneration()` بالای گاردها (بی‌قید و شرط) | bump غیرقابل‌دسترس |
| `Biotak/ObjectCache.mqh` | فیلتر `CacheRebuild` → تست پیشوندِ `inpObjectPrefix` | `'T','H'` |
| `Biotak/BiotakPanels.mqh` | `PnlDestroy` → یک پاک‌سازی پیشوندی، حذف اسکن دوم + ۳۳ پروب | ۲ اسکن + ۳۳ miss |
| `Biotak/BiotakPanels.mqh` | `PnlCloseAll` → **یک** پاک‌سازی خانوادگی به‌جای ۱۴ teardown | ۲۸ اسکن + ~۵۶۰ پروب |

### گیت تأیید — همهٔ ۶ ورودی، هر دو پلتفرم

```
MT5 Full               PASS    err=0 warn=0   28417 ms  1770784 B
MT5 Lite               PASS    err=0 warn=0   14205 ms   633062 B
MT4 Full               PASS    err=0 warn=0    2062 ms  2568712 B
MT4 Lite               PASS    err=0 warn=0    1063 ms   980068 B
MT5 Full (junction)    PASS    err=0 warn=0   23306 ms  1772054 B
MT5 Lite (junction)    PASS    err=0 warn=0   14190 ms   633090 B

```

هر ۶ ورودی **۰ error / ۰ warning**. کامپایل‌ها واقعی بودند (۲۸.۴ ثانیه برای MT5 Full، نه replay
۶۵۰ms). و mtime هر ۴ آرتیفکتِ متمایز **جدیدتر** از آخرین ویرایش منبع است (`19:03:04`) — پس نتیجه
واقعاً به کدِ نهایی مربوط است، نه به build قبلی.

**کرانِ رفتار MT4 دست‌نخورده:** هر سه تغییر «مجموعهٔ حذف‌شده» را **دقیقاً همان** نگه می‌دارند یا
سوپِرستِ آن‌اند (پنجرهٔ `-1`)، و هیچ منطق رندری تغییر نکرده. MT4 Full هم کامپایل تازه و سبز است.

## ۶. اصلاح پنجم — `DeleteHTFCandles` (همان `htf=219ms`)

قاعدهٔ مکملِ بخش ۴ اینجا برعکس عمل می‌کند: **`ObjectsDeleteAll(chart, prefix)` هزینه‌اش با
«کل چارت» رشد می‌کند، ولی کارِ اینجا محدود به «خانوادهٔ HTF» است** — که یک تا دو مرتبهٔ
بزرگی کوچک‌تر است. پس حذف با **نام** ارزان‌تر است.

خانوادهٔ HTF دقیقاً ۵ نام به ازای هر ایندکس دارد (از `DrawHTFCandleCore`):

```
<prefix><i>      <prefix><i>_F      <prefix><i>_B      <prefix>WU<i>      <prefix>WL<i>
```

و **`wickId` خودِ ایندکسِ کندل است** (`string wickId = IntegerToString(i);`) — یعنی این
خانواده **مصون** است: ایندکس و قیمت با هم حرکت می‌کنند، پس اینجا تکرارِ اشتباهِ
R-LEVEL-NAME رخ نمی‌دهد.

اصلاح: برای خانوادهٔ **شناخته‌شده** حذف با نام، و پاک‌سازی پیشوندی **فقط به‌عنوان تور**:

```mql4
if(g_HTFDrawnCount > 0)
{
   HTFDeleteIndices(0, g_HTFDrawnCount);
   g_HTFDrawnCount = 0;
   if(!HTFAnyBoxesExist()) return;   // خانواده کامل حساب شده — بدون اسکن
}
ObjectsDeleteAll(0, g_HTFPrefix);    // تور برای چارتی که نمی‌توانیم حسابش کنیم
```

**تور، همان چیزی است که این را صادق نگه می‌دارد:** `g_HTFDrawnCount` دفترِ خودِ drawer است،
پس چارتی که نتوانیم حسابش کنیم (پیشوندِ کهنه، draw نیمه‌تمام، تمپلیت) باز هم پاک‌سازی
بی‌قیدوشرط می‌گیرد.

`HTFDeleteIndices` از پایین به **بالای** `DeleteHTFCandles` منتقل شد، چون MQL4 اعلان
پیشروِ تمیز ندارد (prototype خالی = `warning 46`) — همان تله‌ای که یادداشتِ P-PERF-14 در
همین فایل ثبت کرده بود.

## ۷. باقی‌مانده

1. **`labels=954ms`** روی resize (SPXUSD H1→M30). `ClearAllLabels` از قبل بهینه است (یک
   bulk + مهاجرتِ stamp‌دار)، پس هزینه در یکی از ۶ تابعِ بعدیِ `RedrawLabelsOnly` است.
   **باید sub-ledger بگذاریم** — به همان روشِ P-PERF-28b — چون قاعدهٔ پروژه این است که
   «عددی که مالک ندارد، مبنای اقدام نیست».
2. **`htf=219ms`** اصلاح شد (بخش ۶) ولی **عددِ بعدی باید تأییدش کند.**
3. **قبل از تحویل، دو تشخیص را خاموش کنید:** `ENABLE_MT5_LEVEL_DUMP` و
   `ENABLE_MT5_PRIMITIVE_PROBE`.
4. ترمینال باید یک‌بار نمونهٔ جدید را بار کند تا `pnl=` و `htf=` تازه اندازه‌گیری شوند —
   **عددِ بعدی، حکمِ نهایی است.** ادعای این سند بر پایهٔ کد و قیمتِ primitive‌هاست، نه بر
   پایهٔ لاگِ بعد از fix.

### قاعدهٔ کامل‌شده

> **پاک‌سازی پیشوندی وقتی خانواده کسرِ بزرگی از چارت است؛
> حذف با نام وقتی خانواده کوچک است — و همیشه یک «تور» باقی بگذار،
> چون دفترِ drawer ممکن است ناقص باشد ولی یک پاک‌سازیِ نام‌محور **نمی‌تواند** نشتی بدهد.**
