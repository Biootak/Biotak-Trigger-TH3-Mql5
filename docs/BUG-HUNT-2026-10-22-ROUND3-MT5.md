## باگ ۱ و ۲ — استریپ بعد از attach برنمی‌گشت

`DrawStripStateRestore` در MT5 این‌طور شروع می‌شد:

```cpp
static bool done = false;
if(done) return;
done = true;          // ← قبل از هر کاری
```

یعنی **اولین فراخوانی همیشه آخرین فراخوانی بود**. MT4 این را به‌عنوان P-UI-146d حل کرده بود:
اولین فریم‌های بعد از attach می‌توانند قبل از آن اجرا شوند که drawing قابلِ‌شمارش باشد یا پنجره
جا برای استریپ داشته باشد؛ پس آن «نیافتم» باید تا ۵ بار، هر یک ثانیه، تکرار شود. در MT5 یک
ازدست‌دادن زودهنگام = استریپ برای تمام عمر چارت بسته. دقیقاً همان شکایتی که با «بعد از تغییر
تایم‌فریم استریپ برنمی‌گردد» شناخته می‌شود.

همچنین MT5 پین را **بعد از** `DrawStripOpen` می‌نوشت. P-UI-146c دلیلش را نوشته است:
`DrawStripOpenAt` پینی را که می‌بیند نگه می‌دارد (`keepPin`) و در **پایان همان پاس** نقاشی
می‌کند؛ پینی که بعد از open نوشته شود، فریم اول را با آیکن و رینگ قدیمی می‌گذارد — و صندلی
`gid==0` هیچ repaint دیگری ندارد، پس همان فریم غلط، دائمی می‌شد.

هر دو یک‌جا پورت شد: بودجهٔ تلاش (۵ بار، ۱ ثانیه فاصله)، `done` فقط به‌معنای «قطعی شد» نه
«تلاش شد»، و پین قبل از open با بازگردانی در صورت شکست.

## باگ ۳ — پایه‌های TP روی نردبان اشتباه

`EventHandlers` سه پایهٔ TP را از `plan.tp1..3` می‌گرفت — یعنی ردیف‌های نردبان **ساختار** —
در حالی که MT4 در `TradePlanTPFromEng` همان نسبت‌ها را روی **حد ضرر خودِ باکس** (`plan.eng`)
حساب می‌کند. عدد روی چارت با عدد در پنل یکی نبود. تابع گمشده به MT5 اضافه شد و سه خط
فراخوانی روی آن سوار شد.

## باگ ۴ — حلقهٔ pump → Sync → story → pump

`BaseKnot_Owner` در MT5 هنوز `an = g_bkBoxes[k].storyT` بود (لبهٔ *داستان*)، در حالی که MT4
با P-BK-115d آن را به `an = t2` (لبهٔ راست باکس) برده بود. هر پاس، story را جلو می‌برد، story
`Sync` را بیدار می‌کرد، `Sync` دوباره `pump` را — یک حلقه. ردیف‌های «توانایی» هم روی
`anStory` جدا رفتند تا خواندنشان تاریخِ داستان بماند و محاسبهشان لبهٔ باکس.

## باگ ۵ — سوئیپ fibo درز داشت، و فنس، sync را بی‌پایان می‌کرد

`FibPenStraysDrop` یک پیمایش `dl = 0..11` بود که برای هر سطح `q = 0,1,2…` می‌پرسید و در
**اولین نام غایب** می‌ایستاد، بعد `_FSC`/`_FSW`/`_FSH` را تک‌تک پروب می‌کرد. دو درز:

1. پشته‌ای که `q=0`اش رفته بود (یا فرزندش روی سطح ۳ بود و سطح ۰ خالی) پیمایش را زود می‌شکست
   و stray‌های پشت درز از هر delete جان سالم به‌در می‌بردند.
2. فنس `if(!dropAll && ObjectFind(...0,0) < 0 && …) return false;` سطح ۰ را می‌پرسید؛ وقتی
   نبود، `return` هم memo را نمی‌نوشت، پس شبکهٔ ۲ ثانیه‌ای هر پاس «pen=0 vs memo=1» می‌دید و
   همان pen مرده را تا ابد دوباره sync می‌کرد.

هر نامی که این واحد می‌سازد با `<master>_FS` شروع می‌شود، پس یک `ObjectsDeleteAll(0, fibo+"_FS")`
جواب هر چهار خانواده و هر درز را می‌دهد و یک پاس لیستِ آبجکت هزینه دارد، نه ~۱۰۰ پروب. فنس
حذف شد؛ حالا خودِ سوئیپ probe است و هر خروج memo را می‌نویسد. گارد فرزند می‌ماند (حذفِ فرزند
هرگز نباید سوئیپ master را راه بیندازد — P-DRAW-74b).

## باگ ۶ — سه نسخه از یک ریاضی

ریل قطار (Tools) در MT5 در سه جا حساب می‌شد: paint (`CircBtnSize`)، fit walk
(`CircRailCapacity`) و hit/placement (`SubRailAxis`). MT4 چهار عدد را **نام‌دار** کرده بود
(`CircRailStep/Lead/Run/Room`) و همه از همان می‌خواندند. نتیجه: تصحیح pitch در یک جا می‌رسید
و در دو جا نه — همان شکلی که P-UI-204 → P-UI-205 را ساخت (پیتچ ۴۱ با تایل ۴۳ = شانه).

چهار تابع نام‌دار به MT5 برگشتند و هر سه جا روی آن‌ها سوار شد:

```cpp
int CircRailStep(const int tile) { return tile + CIRC_GAP; }
int CircRailLead(const int tile) { return CIRC_ORB_SIZE / 2 + tile / 2 + CIRC_GAP; }
int CircRailRun(const int tile, const int n)
{ return CircRailLead(tile) + (n - 1) * CircRailStep(tile) + tile / 2; }
int CircRailRoom(const int freeRun, const int tile) { return freeRun - CIRC_PAD - tile / 2; }
```

و `SubRailPitch()`/`SubRailFirstCentre()` حالا `CircRailStep(SubRailTile())` و
`CircRailLead(SubRailTile())` هستند — عدد یک صاحب دارد، در هر دو درخت.

## باگ ۱۳ — سه `#define` که هیچ‌کس نمی‌خواند

`DrawStrip.mqh` این سه نام را داشت:

```cpp
#define DSTRIP_SLOT_MORE   (-6) // quick: the "..." popover
#define DSTRIP_SLOT_GEAR   (-7) // quick: the full-settings panel
#define DSTRIP_SLOT_PIN    (-8) // quick: pin toggle (stays while editing)
```

`grep -rn` روی **کل** درخت (نه فقط این فایل) فقط همان سه خط تعریف را برمی‌گرداند: صفر خواننده.
ستونِ چهارمشان همیشه صفر است و کد از مسیرهای دیگر می‌رود (`DRAW_SLOT_MORE` و خودِ صندلی‌های
gear/pin). MT4 همین سه را در پاک‌سازی گذشته‌اش **حذف کرده** — فایل `diff-drawstrip.txt` خودِ MT4
این سه را با علامت `-` نشان می‌دهد. یعنی MT5 نسخه‌ای را نگه داشته بود که MT4 دور انداخته بود.

حذف شدند (با یک یادداشت که چرا). نکتهٔ مهم‌تر از خودِ حذف: همین سه، تنها دلیلِ **زرد** ماندن
`DrawStrip.mqh` در گیت بودند. کدِ مرده فقط کدِ مرده نیست — در اندازه‌گیری هم دروغ تولید می‌کند.

## باگ ۱۴ — نقطهٔ انتخابِ ray/path بعد از تغییر تایم‌فریم روی چارت می‌ماند (باگ MT4)

این یکی برعکسِ بقیه است: **MT4 باگ دارد و MT5 ندارد**، و همین باعث می‌شد ابزار در سه ماژول
زرد بدهد (`HRayHandlesWipe`، `PathHandlesWipe`، سه تابع handoff خانوادهٔ HTF).

مکانیزم: نقطهٔ انتخاب یک `BITMAP_LABEL` به نام `<line>_H` است.

- MT4 در `HRayAdoptOrphans` صریحاً `if(HRayIsHandle(nm)) continue;` می‌گذارد — یعنی `_H` هرگز
  adopt نمی‌شود؛ و `OnDeinit` هم `s_hraySel = ""` می‌کند. نتیجه: نقطه‌ای که از سشن قبلی روی
  چارت مانده، نه adopt می‌شود نه حذف — **برای همیشه** با هندسهٔ قدیمی می‌ماند.
- MT5 `HRayHandlesWipe()` / `PathHandlesWipe()` را روی attach و روی هر deinit غیرِ
  `REASON_REMOVE` صدا می‌زند، پس هیچ نقطهٔ یتیمی از انتخابش زنده نمی‌ماند.

نتیجهٔ دیداری یکسان است (نقطه فقط وقتی انتخاب شده هست دیده می‌شود) — با این تفاوت که MT4 در
حالت باگ یک شبح اضافه دارد. این در گیت به‌عنوان نمادِ MT5-only **اعلام** شد، با همین دلیل مکتوب،
نه به‌عنوان اختلافِ سرخ.

سه تابع `HTFKeptStampName` / `SaveHTFHandoffStamp` / `HTFAdoptKeptFamily` هم از همین جنس‌اند
ولی دلیلشان ساختاری است: MT5 در تغییر تایم‌فریم نمونه را نابود و از نو می‌سازد، پس شمارشِ
خانوادهٔ HTF نمی‌تواند از طریق static به نمونهٔ بعد برسد. یک کلید chart-keyed آن را یک‌بار
منتقل می‌کند؛ MT4 همان نمونه را نگه می‌دارد و مستقیم `g_HTFDrawnCount` را می‌خواند.

## پاسخ به سؤال اصلی: از کجا مطمئن شویم تک‌تک خط‌ها بررسی شده؟

این سؤال دو نیمه دارد و باید صادقانه از هم جدا شوند.

### نیمهٔ اول — چیزی که عدد می‌دهد (اندازه‌گیری‌شده)

هر خط در یکی و فقط یکی از این پنج سبد می‌افتد، و ابزار تعداد هر سبد را **per module** چاپ
می‌کند:

| سبد | معنی | چطور سنجیده می‌شود |
|---|---|---|
| **shared** | متنِ یکسان در هر دو درخت | multiset خط‌ها، بی‌ترتیب و بی‌فاصله |
| **ENGINE** | داخل `#ifdef BIOTAK_RENDER_ENGINE` | شمارشگر بلوکِ شرطی، جدا چاپ می‌شود |
| **declared MT5-only** | مکانیزمی که فقط MT5 لازم دارد (پژواک OBJECT_DELETE، handoff، stopwatch) | رجیستری با دلیلِ مکتوب، هر ورودی نام‌دار |
| **declared rewrite** | یک نماد کامل که الگوریتم دیگری با **همان نتیجه** دارد | رجیستری با دلیلِ مکتوب، هر ورودی نام‌دار |
| **logging** | `Print`/`DrawStripDiagEmit` و ادامهٔ خطوطش | **متقارن** در هر دو سمت حذف می‌شود |

نتیجهٔ اندازه‌گیری: سبد ششم — «خطی که در هیچ‌کدام نیست» — **خالی است**. این یک ادعای قابل
تکرار است: `python tools/parity/module-report.py` هر بار `0 RED, 0 YELLOW, 78 GREEN, 0 MT5-only files`
می‌دهد یا نمی‌دهد. همچنین `dead-locals` صفر است، `check-pp-balance` روی هر ۷۶ فایل
`final depth = 0` می‌دهد و هر دو ورودی با `0 errors, 0 warnings` کامپایل می‌شوند.

تفکیک «سرخ» و «زرد» عمدی است و معنای متفاوتی دارد:

- **سرخ** = یک خط یا یک نماد در MT4 هست و در MT5 نیست، بدون توضیح. یعنی **منطق گم‌شده**.
- **زرد** = نمادی در MT5 هست که MT4 ندارد، و در سطح **نماد** اعلام نشده (حتی اگر خط‌هایش
  اعلام شده باشند). یعنی **افزودهٔ بی‌سند**. باگ ۱۳ و ۱۴ نشان دادند که زرد را نباید نادیده
  گرفت: هر شش موردِ زرد یا کدِ مرده بود یا کارِ واقعیِ MT5 که سند نداشت.

### نیمهٔ دوم — چیزی که عدد نمی‌دهد (استدلال خوانده‌شده)

ابزار نمی‌تواند بررسی کند که «دلیلِ» یک ورودی اعلام‌شده **راست** است. آن یک قضاوت انسانی
است. برای همین هر ورودی اعلام‌شده، رفتارِ مشخصی را نام می‌برد که حفظ می‌شود، نه یک برچسب
کلی. مثلاً:

- `DeleteLegacyMenuObjects` — «یک `ObjectsDeleteAll` روی پیشوند، که **ابر-مجموعهٔ** لیست
  دستیِ MT4 است».
- `TH3FamilyDeleteAll` — «مدل + کپشن + ردیف‌های کانواس + آبجکت‌ها + اشاره‌گر active؛ نسخهٔ
  خطیِ MT4 در بعضی مسیرها store و کانواس را جا می‌انداخت و خانواده در restore برمی‌گشت».
- `OnABCDMouseEvent` — «درگ از طریق یک نقطهٔ زندهٔ قفل‌شده با اعمال ۲۰ms، چون MT5 لبهٔ
  button-up قابل‌اعتماد برای درگ نمی‌دهد».

پس پاسخ دقیق: **هر خط در یک سبدِ نام‌دار افتاده و سبدِ «ناشناخته» صفر است** — این را عدد
می‌گوید. اما **درستیِ هر سبدِ اعلام‌شده** را باید کسی بخواند؛ کاری که در این دور برای هر
نمادِ اعلام‌شده انجام شد و دلیلش کنار خودش نوشته شد، تا دورِ بعد قابلِ بازبینی باشد.

### حلقه‌ها

۵۶ نقطهٔ `while(` باز شد. چهار `while(true)` متنی (`BaseKnotTool`، `DrawToolbar`، `PenStack`)
پیمایش رشته‌اند و `at` همیشه جلو می‌رود (`pos = at + 1`) — بی‌نهایت نمی‌شوند. حلقه‌های
تخلیهٔ قفل (`while(g_ChartLockCount > 0) CircUnlockChart();`) فراخوانِ خود را بی‌قید کم
می‌کنند، پس تمام می‌شوند.

### تقسیم‌ها

`div-guard.py` ۱۱۴ نامزد می‌دهد. همهٔ نامزدهای «مقسوم‌علیه شمارشی» دستی خوانده شدند و هر
کدام یا داخل `if(x > 0)` یک‌خطی بود (که regex نمی‌بیند)، یا مقسوم‌علیه با ثابتِ ALL-CAPS، یا
مقدارش قبلاً اثباتاً مثبت است. یک نمونهٔ واقعی از این کلاس در دور قبل بسته شد (P-BE-05،
`segW` در `PnlUpdateRow`).

هر باینری MetaQuotes که از فرایندِ agent اجرا شود با `0xC0000139`

یکسان‌اند (`md5 13f0e60a…`، 5.0.0.6230).

راهِ حلِ استفاده‌شده: کامپایل از طریق **Task Scheduler** در نشست تعاملیِ کاربر:

powershell -NoProfile -ExecutionPolicy Bypass -File tools/mt5-sched-build.ps1 -Source "Biotak Trigger TH3.mq5"
powershell -NoProfile -ExecutionPolicy Bypass -File tools/mt5-sched-build.ps1 -Source "Biotak Trigger TH3 Lite.mq5"

دوبار کلیک روی `.mq5`) باز کنید. کپی‌شدنِ `MetaEditor64.exe` داخل پوشهٔ پروژه هم یک علت
دوم است — آن کپی را پاک کنید و از نسخهٔ نصب‌شده استفاده کنید.

## دو باگ در خودِ ابزار سنجش

1. **پایان‌بخشِ chunk، کامنت را هم می‌خواند.** `int F() { return X; }   // note` با `note`
   تمام می‌شد نه با `}`؛ پس chunk هر تابع بعدی را می‌بلعید و گزارش آن‌ها را «در MT5 نیست»
   می‌نامید. حالا کامنتِ انتهاییِ آگاه‌به-کوتیشن حذف می‌شود.
2. **`norm_body` رشته می‌خواهد، نه لیست.** فراخوانی با لیست، `AttributeError` می‌داد.

هر دو رفع شد؛ بدون این دو، عددِ «۲۴ سرخ» بخشی‌اش دروغِ ابزار بود، نه واقعیتِ کد.
